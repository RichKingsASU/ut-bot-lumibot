## Five findings that change the migration

### 1. pg_partman drives a partitioned table

`ohlcv_bars` is partitioned, with monthly partitions `p20251201` … `p20261001`
plus `ohlcv_bars_default`, created by **pg_partman 5.3.1** and maintained by the
hourly `partman-maintenance` cron job.

A dump/restore that copies tables but not the partman config and cron job would
appear to succeed, then **stop creating partitions**. Inserts keep working until
the last pre-created partition is passed, then fail — well after cutover, when
the cause is no longer obvious.

Migrating `ohlcv_bars` means migrating pg_partman config (`part_config`,
`part_config_sub`, `template_public_ohlcv_bars`) and re-establishing scheduled
maintenance. Cloud SQL supports pg_partman as an extension, but its scheduler
is pg_cron, which must be enabled and configured separately.

### 2. Three active pg_cron jobs

    [2] 0 * * * *      partman-maintenance     hourly partition maintenance
    [3] 30 11 * * 1-5  refresh-open-interest    weekdays, market hours
    [4] * * * * *      hitl_queue_expire_job    every minute

`hitl_queue_expire_job` runs every 60s against `hitl_queue` — the
human-in-the-loop gate (`HITL_ENABLED` is set on k2). If it stops, HITL entries
stop expiring. That is a trading-safety behaviour, not a cosmetic one.

None of these are visible through PostgREST. A REST-only audit would have
migrated the data and silently dropped all three.

### 3. Two publications exist

    supabase_realtime
    supabase_realtime_messages_publication

Logical replication is therefore feasible for Cloud SQL cutover (Method B),
not just pg_dump baseline. Both are Supabase-managed for Realtime; a migration
publication should be created separately rather than reusing these.

### 4. RLS drift: 70 live vs 60 in migrations

`pg_policies` reports 70 policies; `supabase/migrations/*.sql` contains 60
`CREATE POLICY` statements. Ten policies exist in the live database that are
not reproducible from the migration files.

**The migration files are not a complete source of truth for security.** Port
RLS from `pg_policies`, not from the repo.

### 5. Extensions to verify against Cloud SQL

    supabase_vault 0.3.1     Supabase-specific; no Cloud SQL equivalent
    wrappers 0.5.7           Supabase foreign-data wrappers

Both are Supabase platform extensions. Confirm what actually uses them before
assuming the schema ports; `supabase_vault` in particular may hold secrets that
need relocating to Secret Manager.

Cleanly portable: `pg_cron`, `pg_partman`, `pg_stat_statements`, `pgcrypto`,
`plpgsql`, `uuid-ossp`.

## Classification

`database-objects.csv` classifies every object as APPLICATION,
SUPABASE_PLATFORM or SYSTEM. Platform schemas (`auth`, `storage`, `realtime`,
`vault`, `graphql`, `extensions`, `cron`, `pgsodium`, …) are **not** migration
candidates — their functionality is replaced by GCP services rather than
reproduced in Cloud SQL.
